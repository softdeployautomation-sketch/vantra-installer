# Vantra → MSI Generator Integration Spec

This document is for the engineer making changes to the **Vantra web app** repo
(`Mikeolab/vantra`). It tells you exactly what to change, what contract to implement,
and why each decision was made.

Read this alongside the MSI builder work in `msi-builder/` and `generator/` in this repo.

---

## What's changing and why

Today the "Add Device" flow gives users a direct download link to a `.exe` generated by
TacticalRMM. That EXE is flagged by antivirus software because it uses a generic community
signing certificate.

The new flow replaces that `.exe` link with a signed `.msi` built by a generator service
on the Vantra VPS. The MSI is a proper Windows installer — cleaner, signable with your
own org certificate, and less likely to be flagged.

The user now uploads their own PDF guide when creating a deployment. That PDF gets baked
into the MSI so the customer gets it as part of the install.

---

## What Vantra already has (no extra API calls needed)

When a deployment is created today, all the data the MSI generator needs is already
available in Vantra's codebase. You do not need to fetch anything extra from TacticalRMM.

| MSI generator needs | Where it comes from in Vantra |
|---|---|
| `--client-id` | `user.trmmClientId` (already on the `User` row) |
| `--site-id` | `user.trmmSiteId` (already on the `User` row) |
| `--agent-type` | `parsed.agentType` from the deployment request |
| `--auth` | The `uid` returned by `createDeployment()` in `lib/trmm.ts` — this IS the auth token |
| `--api` | `env.trmmApiBaseUrl` (`TRMM_API_BASE_URL` env var) |
| `--manufacturer` | Hard-code as `"VANTRA"` — no input needed |
| PDF file | Uploaded by the user in the modal (new) |

The deployment UID from TacticalRMM is both used in the download URL today
(`/clients/{uid}/deploy/`) and serves as the `--auth` token in the install command. It
expires in 72 hours (configurable via `DEPLOYMENT_EXPIRY_HOURS`).

## Files to change in `Mikeolab/vantra`

### 1. `components/add-device-modal.tsx`

**Add a PDF file input to the modal.**

Before the user clicks "Generate installer", show a file upload input:

```
Label: "Upload your install guide (PDF)"
Input: type="file", accept=".pdf", required
```

- The field is required — do not allow form submission without a PDF selected.
- Show a brief description: "This PDF will be included in the installer and added to the
  customer's Start Menu."
- The file is sent to the API as part of a `multipart/form-data` request (see API change
  below), not as JSON.
- Change the `createInstaller()` function to use `FormData` instead of
  `JSON.stringify(...)`. Example:

```ts
const form = new FormData();
form.append("agentType", "workstation");
form.append("goarch", "amd64");
form.append("pdf", pdfFile);           // pdfFile is the File from the input

const res = await fetch("/api/devices/deployments", {
  method: "POST",
  body: form,
  // Do NOT set Content-Type manually — browser sets it with the correct boundary
});
```

- The `InstallerResult` type doesn't need to change — the response shape stays the same,
  but `downloadUrl` now points to the generated `.msi` instead of the TacticalRMM `.exe`.
- Show the file name and size next to the input once selected so the user can confirm
  they picked the right file.
- Add basic client-side validation: reject files over 20 MB before sending (the generator
  will also enforce this, but failing fast in the browser is better UX).

### 2. `app/api/devices/deployments/route.ts`

**Accept multipart form data, pass PDF + params to the MSI generator, return MSI URL.**

Replace the current `request.json()` call with multipart parsing. Next.js App Router
does not parse multipart automatically — use `request.formData()`:

```ts
const form = await request.formData();
const agentType = form.get("agentType") as string;
const goarch    = form.get("goarch") as string;
const pdfFile   = form.get("pdf") as File | null;
```

Validate:
- `pdfFile` must be present, must be `application/pdf` or filename ending `.pdf`, and
  must be under 20 MB.
- `agentType` and `goarch` still go through the existing Zod schema (adjust to parse
  from form fields, not JSON body).

**After calling `createDeployment()` and getting back `uid`**, instead of returning the
TacticalRMM download URL directly, call the MSI generator:

```ts
const msiUrl = await callMsiGenerator({
  clientId:     user.trmmClientId!,
  siteId:       user.trmmSiteId!,
  agentType:    parsed.agentType,
  authToken:    uid,                    // deployment UID = auth token
  apiUrl:       env.trmmApiBaseUrl,
  manufacturer: "VANTRA",
  pdf:          pdfFile,
});
```

Return `msiUrl` as the `downloadUrl` in the response — the shape stays identical to what
the modal already handles.

**`callMsiGenerator()` — implement this as a helper in `lib/msi-generator.ts`** (new file).
See the contract section below.

**Error handling:**
- If the generator call fails, do NOT roll back the TRMM deployment (it's already created
  and can't be un-created cleanly). Instead, log the error and return a 502 with a
  user-facing message: `"Installer was created but packaging failed. Please try again."`
- The `Deployment` row should still be written to the DB (for accounting/limits), but add
  a `msiReady` boolean field (see schema change below) that is `false` if packaging failed.

### 3. `lib/msi-generator.ts` (new file)

HTTP client for the MSI generator service. Example shape:

```ts
import "server-only";
import { env } from "./env";

export async function callMsiGenerator(opts: {
  clientId:     number;
  siteId:       number;
  agentType:    string;
  authToken:    string;
  apiUrl:       string;
  manufacturer: string;
  pdf:          File;
}): Promise<string> {
  const form = new FormData();
  form.append("clientId",     String(opts.clientId));
  form.append("siteId",       String(opts.siteId));
  form.append("agentType",    opts.agentType);
  form.append("authToken",    opts.authToken);
  form.append("apiUrl",       opts.apiUrl);
  form.append("manufacturer", opts.manufacturer);
  form.append("pdf",          opts.pdf);

  const res = await fetch(`${env.msiGeneratorUrl}/build`, {
    method: "POST",
    headers: { Authorization: `Bearer ${env.msiGeneratorSecret}` },
    body: form,
  });

  if (!res.ok) {
    const text = await res.text().catch(() => "");
    throw new Error(`MSI generator ${res.status}: ${text.slice(0, 200)}`);
  }

  const data = await res.json() as { downloadUrl: string };
  return data.downloadUrl;
}
```

Add both vars to `lib/env.ts`:

```ts
msiGeneratorUrl:    required("MSI_GENERATOR_URL"),
msiGeneratorSecret: required("MSI_GENERATOR_SECRET"),
```

And to `.env.example`:
```
MSI_GENERATOR_URL=http://localhost:4000
MSI_GENERATOR_SECRET=change-this-to-a-long-random-string
```

`MSI_GENERATOR_SECRET` must match `GENERATOR_SECRET` in the generator service's `.env`.
Generate a long random value — treat it like a password, never commit it to git.

### 4. `prisma/schema.prisma`

Add `msiReady` to the `Deployment` model:

```prisma
model Deployment {
  id                String   @id @default(cuid())
  userId            String
  user              User     @relation(fields: [userId], references: [id])
  trmmDeploymentUid String   @unique
  monType           String
  goarch            String
  expiresAt         DateTime
  createdAt         DateTime @default(now())
  msiReady          Boolean  @default(false)   // true once generator returns successfully

  @@index([userId, expiresAt])
}
```

Write and run a migration:
```
npx prisma migrate dev --name add_msi_ready_to_deployment
```

Update `route.ts` to set `msiReady: true` on the `db.deployment.create()` call only when
the generator succeeds.

## MSI generator HTTP contract

The generator service lives in the `generator/` folder of this repo (Phase 3, to be
built). Vantra calls it. This is the contract both sides must implement.

### `POST /build`

**Request:** `multipart/form-data`

| Field | Type | Description |
|---|---|---|
| `clientId` | string (numeric) | TacticalRMM client ID |
| `siteId` | string (numeric) | TacticalRMM site ID |
| `agentType` | `"workstation"` or `"server"` | Agent monitoring type |
| `authToken` | string | Deployment UID — used as `--auth` token |
| `apiUrl` | string | TacticalRMM API base URL |
| `manufacturer` | string | Installer manufacturer name |
| `pdf` | file | Customer guide PDF, max 20 MB |

**Success response:** `200 OK`, `application/json`

```json
{
  "downloadUrl": "https://your-vps.example.com/downloads/VantraAgent-abc123.msi",
  "expiresAt": "2026-09-05T12:00:00Z"
}
```

`downloadUrl` is a URL the customer's browser can download directly. The generator
serves the MSI file at that URL. It should be valid for at least as long as the TRMM
deployment token (72 hours by default).

**Error response:** `4xx` or `5xx`, `application/json`

```json
{ "error": "Human-readable error message" }
```

**Timeout:** Vantra should set a 60-second timeout on this call — an MSI build
typically takes 5–15 seconds, but allow headroom for a slow VPS.

**Size limit:** Generator must reject PDFs over 20 MB with a `413` response.

## What NOT to change

- Do not change the `deployUrl()` function in `lib/trmm.ts` — it's still used internally
  by the existing `createDeployment()` function and should not be removed yet.
- Do not change the `Deployment` DB model beyond adding `msiReady` — do not add the PDF
  file path or MSI path to the DB. File lifecycle is the generator's responsibility, not
  Vantra's.
- Do not change the `InstallerResult` type in `add-device-modal.tsx` — the response shape
  stays the same. The modal just uses `downloadUrl` as a link; it doesn't care whether it
  points to a `.exe` or `.msi`.

---

## Rollout order

1. Build and test the generator service locally first (see `msi-builder/` and the coming
   `generator/` implementation). Get a real `.msi` out of it before touching Vantra.
2. Deploy the generator service to the VPS. Set `MSI_GENERATOR_URL` in Vantra's env.
3. Apply the Prisma migration.
4. Ship the Vantra changes.

Do not ship the Vantra changes before the generator is live — the `callMsiGenerator()`
call will throw on every deployment creation if `MSI_GENERATOR_URL` is unreachable.

## Open questions to resolve with the product owner

- Should old deployments (created before this change) still show a download link in the
  dashboard? Currently `msiReady=false` deployments have no download URL stored. Either
  hide them or show a "re-generate" option.
- Should the PDF upload be optional (fall back to a default Vantra guide PDF on the
  server) or always required? The current spec makes it required.
- Is 20 MB the right PDF size cap? Most single-page install guides are under 2 MB — 20 MB
  is generous but you may want to tighten it.
